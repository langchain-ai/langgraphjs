`StreamOrchestrator` runs no longer ask for `values` when the messages are the only state key shown (`stateKeys: []`) and `messages-tuple` streams them, as with `@langchain/react` 2.0. A `values` event carries the whole state after every step, so on a long thread each step sent the whole thread again: one 22-message turn on a 1,350-message thread took 70 MB in the browser, and 3.6 MB without `values`, most of it one read of the thread as the run ends. The run's messages come from `messages-tuple` and its interrupts from its root `updates`, and a run that streamed no `values` reads the thread's head once as it ends, joined runs included, so the order its parallel steps saved and anything the stream missed come from the server. A stream's first output drops the interrupts an earlier run left, as its first root `values` did. A panel on a subagent or subgraph opened during such a run shows nothing until it has read what that subgraph saved, then that with what streamed meanwhile on top, and reads it again when the run ends, also when the engine can't tell which modes a joined run streams, and subgraphs are found from their nodes' `updates`. An optimistic input shows as sent once the run's first step streams. Runs the engine joins keep the modes they were started with. Apps that don't set `stateKeys`, list other keys, or pass `values` in `submit()`'s `streamMode` get `values` as before.

A message whose `messages` event names no namespace now belongs to the graph its metadata names without the segment of the task that wrote it, as in LangGraph. The tools node's own `ToolMessage` (`tools:<task id>`) was taken for a subagent's: the main conversation left it out until the next `values` event, and a subagent panel on a server that doesn't filter by namespace showed its `task` result.
